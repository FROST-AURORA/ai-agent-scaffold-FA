根据 demo.yml 描述模板，配置一个 agent-draw-io.yml 智能体。用户和智能体对话，发起绘图诉求，也可以在绘图过程中引用拼团营销系统的接口、业务流程和数据。

要求如下：

1. 智能体返回消息必须是 JSON 结构，类型区分为 user、drawio。
    - user：表示信息不足，需要前端继续向用户追问。
    - drawio：表示已经生成 Draw.io XML 内容，前端可以直接渲染到 draw.io 面板。

2. 如果智能体不能确认用户具体绘图诉求，或者缺少拼团接口调用所需参数，则必须返回 user 类型，让用户补充信息。
   示例：
   {"type":"user","content":"请补充要绘制的图类型，例如流程图、时序图、UML 类图，或说明你想分析的拼团业务场景。"}

3. 智能体需要支持通用绘图能力，包括但不限于：
    - UML 类图
    - 时序图
    - 流程图
    - 架构图
    - 状态流转图
    - 接口调用链路图
    - 业务流程图

4. 智能体需要支持引用拼团营销系统能力。用户提到“拼团”“营销配置”“锁单”“结算”“退单”“组队”“活动”“商品试算”等意图时，需要优先判断是否需要调用拼团 MCP 或检索拼团项目上下文。

5. 拼团 MCP 能力建议包含以下工具：
    - gbm_query_market_config：查询拼团营销配置，无副作用，可以主动调用。
    - gbm_query_api_schema：查询拼团接口字段说明，无副作用，可以主动调用。
    - gbm_query_trade_flow：查询拼团业务流程说明，无副作用，可以主动调用。
    - gbm_lock_market_pay_order：营销锁单，有副作用，必须用户明确确认后才能调用。
    - gbm_settlement_order：营销结算，有副作用，必须用户明确确认后才能调用。
    - gbm_refund_order：营销退单，有副作用，必须用户明确确认后才能调用。

6. 对于拼团接口调用，智能体必须进行参数校验：
    - 查询拼团配置需要：userId、source、channel、goodsId。
    - 锁单需要：userId、source、channel、goodsId、activityId、outTradeNo、notifyConfigVO，可选 teamId。
    - 结算需要：userId、source、channel、outTradeNo、outTradeTime。
    - 退单需要：userId、source、channel、outTradeNo。

7. 对于有副作用的拼团操作，例如锁单、结算、退单，智能体不能直接执行。必须先返回 user 类型，让用户确认操作和参数。
   示例：
   {"type":"user","content":"锁单会创建预支付订单。当前参数为 ...，请确认是否继续执行锁单。"}

8. 用户的请求信息需要经过：意图识别、上下文检索、参数判断、业务分析、绘图规划、Draw.io XML 生成、质量检查。

9. 如果用户只是要求“画拼团锁单流程图”“画拼团结算时序图”“画拼团退单状态流转图”，智能体应优先使用拼团项目上下文或拼团 MCP 查询业务流程，不需要真实执行交易接口。

10. 绘图完成后必须检查：
- Draw.io XML 是否格式正确。
- 节点是否重叠。
- 连线是否明显交叉。
- 业务流程方向是否清晰。
- 拼团接口、领域服务、仓储、MQ、回调等节点关系是否合理。

11. 最终输出必须严格符合以下 JSON 之一：
- 需要用户补充：
  {"type":"user","content":"请补充 ..."}
- 可以渲染 Draw.io：
  {"type":"drawio","content":"这里放最终 Draw.io XML 字符串"}

综上，基于该场景，需要区分多个单一职责智能体，例如意图识别智能体、拼团上下文智能体、绘图规划智能体、Draw.io 生成智能体、质量检查智能体。之后可以通过串行、循环、并行工作流组合这些智能体，用于获得更准确的拼团业务图和通用图表。
